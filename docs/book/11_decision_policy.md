## 1장. 바닥부터: 공중전·관측·전술·정책

### 1.1 우리가 푸는 문제
전투기 두 대가 하늘에서 1:1로 싸운다(WVR = Within Visual Range, 시계 내 근접전). 우리는 그 중
한 대를 자동으로 조종하는 두뇌를 만든다. 두뇌가 하는 일은 매 순간 "지금 무엇을 할까"를 정하는 것.

이기는 법(규칙)은 정해져 있다:
- WEZ(Weapon Engagement Zone, 무장교전구역): ATA 12도 미만이고 거리 500에서 3000ft 면 피해 발생.
  피해율(초당) = 25 곱하기 거리계수 곱하기 각도계수. 거리계수 = (3000 빼기 거리) 나누기 2500,
  각도계수 = 1 빼기 ATA 나누기 12 (둘 다 선형, 가까울수록·정조준일수록 큼). 초당 25는 500ft·0도의
  최댓값. 적 앞 12도, 가까운 거리에 오래 머무르면 피해가 커져 이긴다.
- Hard Deck(최저고도): 고도가 1000ft 밑으로 내려가면 *그 즉시 패배*(지면 충돌 간주).

즉 목표는 "적을 내 12° 원뿔 안, 500~3000ft에 붙잡아 두기 + 나는 절대 너무 낮아지지 않기".

### 1.2 "결정"의 단위 — tick(틱)
컴퓨터는 연속이 아니라 *잘게 쪼갠 순간*마다 판단한다. 그 한 순간을 tick(틱) 이라 한다.
우리 시스템의 세 가지 시계:
- 물리 120Hz — JSBSim(비행 시뮬레이터)이 1초에 120번 비행 방정식을 푼다(가장 잘게).
- 제어 20Hz — 0.05초마다 조종면(타·throttle)을 갱신.
- BT 결정 10Hz — 0.1초마다 "전술"을 다시 고른다. ← 우리 BT가 호출되는 주기.

> 핵심: 우리 BT는 1초에 10번 호출된다. 그래서 "한 번 정하면 끝"이 아니라 *계속 다시 정한다*(7장).

### 1.3 관측(Observation) — 우리가 보는 숫자들
매 결정 때 우리 BT는 적과의 기하(geometry)를 숫자로 받는다. 핵심 7개를 그림으로 정의한다.

```
                      적기 (기체) (진행방향 →)
                     ╱
            거리   ╱   ← distance_ft (두 기체 사이 거리, ft)
                 ╱
   내 기수 →  (기체)────────  내 진행방향
   
  · ATA (Antenna Train Angle) : "내 기수"와 "적 방향" 사이 각. 0°=적을 정조준. (내가 적을 얼마나 겨눴나)
  · AA  (Aspect Angle)        : "적 꼬리"와 "나" 사이 각. 0°=내가 적 정후방(6시). 180°=적 정면.
  · HCA (Heading Crossing Angle): 두 기체 진행방향 사잇각. 0°=같은 방향, 180°=정반대.
  · closure (접근속도)         : 거리가 줄어드는 속도. +면 다가옴, −면 멀어짐(도망).
  · es_diff (에너지 차)        : (내 고도+속도에너지) − (적 고도+속도에너지). +면 내가 유리.
  · ego_r_dps / enm_r_dps      : 나/적의 yaw rate(선회 각속도, °/s). 누가 어느 쪽으로 얼마나 도나.
```

직관 요약:
- ATA 작다 = 내가 적을 겨눴다(공격 기회). ATA 크다 = 적이 내 옆/뒤(나쁨).
- AA 작다 = 내가 적 꽁무니(유리). AA 크다(180 근처) = 적이 나를 마주 봄(정면/위험).
- 거리·closure = 멀어지나 가까워지나. es_diff = 에너지 우열. yaw rate = 선회 의도.

이 숫자들이 1장 이후 모든 판단의 입력이다. (전체 키·단위·부호: [TACTIC_SPEC](../../new_match_engine/TACTIC_SPEC.md))

### 1.4 전술(Tactic)이란
전술(Tactic) = "지금 하고 싶은 한 가지 기동의 *이름*". 예: `GUN_TRACK`(조준 추격),
`CLIMB`(상승), `VERTICAL_PURSUIT`(수직 추격), `ADAPTIVE`(혼합 기동). 전술은 *추상 목표*일 뿐,
아직 조종면 움직임이 아니다(그건 9장에서 변환). 우리 시스템엔 16종의 전술이 정의돼 있다(8장 카탈로그).

### 1.5 정책(Policy)이란
정책(Policy) = "관측을 넣으면 행동을 돌려주는 함수". 수식으로 `행동 = π(관측)`.
우리 BT가 바로 이 π다: `Tactic = TreePolicy.select(관측)`. 그림으로:

```
   관측(7+숫자)  ──►  π = TreePolicy  ──►  Tactic 1개
```

이 장의 결론: 우리 BT는 "관측 → 전술" 정책 함수이고, 0.1초마다 호출된다. 나머지 장은 이 함수의
*내부가 어떻게 생겼고(정의)* *매번 어떻게 답을 내는지(동작)*를 판다.

## 2장. 우리 BT의 정체 — "BT" 세 가지 구분

### 2.1 왜 헷갈리나
이 프로젝트에서 "BT"가 세 군데서 쓰인다. 섞으면 길을 잃는다. 명확히 못 박는다:

| 이름 | 정체 | 파일 | 누가 쓰나 |
|---|---|---|---|
| ① TreePolicy (우리 정책) | 관측→전술 결정기. 이 교과서의 주인공 | `bt/tree_policy.py` | 우리 기체 |
| ② `.yaml` BT (적 트리) | Selector/Sequence/Condition/Action 으로 그린 규칙 트리 파일 | `opponents/*.yaml` | 적 기체 |
| ③ yaml_bt (해석기) | ②의 `.yaml`을 읽어 전술로 바꾸는 인터프리터 | `bt/yaml_bt.py` | ②를 실행 |

### 2.2 셋의 관계
- 우리 기체 = ① TreePolicy 로 전술 선택.
- 적 기체 = ② `.yaml` 파일을 ③ yaml_bt 가 해석해 전술 선택.
- 사람이 ②를 *마우스로 그려 만드는 도구* = bt-editor(웹 편집기). ②/③의 어휘(조건32·액션25)는 100% 정합.

> 그래서 "우리 마지막 BT가 어떻게 정의·동작하나"의 답은 전적으로 ① TreePolicy다. 3장부터 끝까지 ① 이야기.

### 2.3 한눈 구조
```
                        ┌──────────────── 우리 기체 ────────────────┐
   관측 ─►  ① TreePolicy.select()  ─►  Tactic  ─►  guidance ─► LQR/INDI ─► JSBSim
                                                                              │ (같은 물리)
   관측 ─►  ③ yaml_bt(②.yaml)      ─►  Tactic  ─►  guidance ─► LQR/INDI ─► JSBSim
                        └──────────────── 적   기체 ────────────────┘
```
우리와 적은 전술을 고르는 머리만 다르고(①  vs ②③), 전술→비행 변환은 동일하다(공정 비교).

## 3장. 정의(I): 왜 하이브리드인가

### 3.1 우리 BT는 "그림 트리"가 아니다
"행동트리(Behavior Tree)"라는 말 때문에 *마우스로 그린 트리*를 떠올리기 쉽다. 하지만 우리 정책(①)은
트리 그림이 아니라 두 조각을 합친 하이브리드 프로그램이다:

```
   우리 BT(TreePolicy)
     ├─ (A) 규칙 조각   : "이런 상황엔 무조건 이 전술" — 손으로 박은 if-then 4개
     └─ (B) 학습 조각   : "나머지 일반 상황" — 데이터로 배운 모델이 점수로 고름
```

### 3.2 왜 둘을 합쳤나 (설계 동기 = 실패에서 배움)
- 순수 학습만으로 했더니, *명백한 정답이 있는 상황*에서 모델이 흔들렸다(예: 정면 매치에서
  전술이 깜빡임 → 패배). 계측: 정면을 일관 commit 하면 4/4 승, 도중 전환하면 1/4.
- 순수 규칙만으로는, 손으로 모든 상황을 나눌 수 없다(공중전은 상황의 *연속적 조합*).
- → 확실한 4개는 규칙으로 강제(우선순위 위), 나머지는 학습으로 결정(아래). 이것이 우리 BT 정의의 뼈대.

### 3.3 "상황 독립 dispatch"라는 이름의 뜻
규칙 조각을 우리는 상황 독립 디스패치라 부른다. *상황마다 독립적으로 옳은 전술을 강제*한다는 뜻.
"전역 강화(모든 상황에 한 전술을 더 세게)"는 한 상황을 좋게 하면 다른 상황을 망친다는 교훈에서 나왔다.
→ 그래서 *상황을 나눠 각각 다른 전술*을 박는다.

## 4장. 정의(II): 학습 조각은 어떻게 만들어졌나

### 4.1 핵심 원칙: 무거운 계산은 *경기 전*에
경기 중(online)에는 *예측도 rollout(미래 시뮬레이션)도 하지 않는다*. 매 tick 모델에 숫자 한 번 넣고
답을 받을 뿐(μs). 대신 경기 전(offline) 에 무겁게 계산해 "어떤 상황에 어떤 전술이 좋은지"를
배워 가벼운 모델로 구워 둔다.

### 4.2 오프라인 파이프라인 4단계 (각 단계의 "왜")
```
(1) 데이터 수집  → (2) 라벨링  → (3) 회귀 학습  → (4) 굽기(deploy)
```
1. 데이터 수집 (`build_situation_dataset.py`): 다양한 시작 상황에서 매치를 돌려
   `(상황특징, 시도한 전술, 결과)` 를 잔뜩 모은다. *왜?* 모델이 배울 "경험"이 필요.
2. 라벨링 (`offline_solver.py`): 각 상황에서 *전술마다 forward-sim*(앞으로 짧게 시뮬)해
   "이 전술의 가치(점수)"를 매긴다. *왜?* 정답(어떤 전술이 더 좋은가)을 숫자로 만들어야 학습 가능.
   (상황을 KMeans로 6묶음으로 군집해 대표 상황을 추리기도 함 — `cluster_situations.py`.)
3. 회귀 학습: sklearn 회귀모델을 `특징 8개 → 전술별 점수`로 학습. *왜 회귀(점수)인가?*
   "어떤 전술" 한 개를 바로 고르게(분류) 하지 않고 *전술마다 점수*를 내게 해, 실행 시 argmax(최고점)로
   고르면 *왜 그 전술인지*가 점수로 설명된다(투명성).
4. 굽기: 학습한 모델을 `bt/policy_value.pkl` 로 저장. 경기 중엔 이 파일을 불러 `predict` 1번.

### 4.3 산출물 — `policy_value.pkl` 의 구조
```python
d = pickle.load(open("bt/policy_value.pkl","rb"))
d["reg"]      # 학습된 회귀모델 (특징 8개 → 전술별 점수 벡터)
d["feats"]    # 입력 특징 이름 목록 (순서 = 5장의 8개)
d["tactics"]  # 점수 벡터의 각 칸이 어떤 Tactic 인지 이름 목록
```
즉 학습 조각의 실체 = 이 한 파일. 규칙 조각(4개 if-then)은 `tree_policy.py` 코드에 박혀 있다.

## 5장. 정의(III): 입력 특징 8개 완전 해설

학습 조각(회귀)이 보는 입력은 *정확히 8개*다. 각각 "무엇을·왜·크면/작으면" 으로 푼다.

| # | 특징 | 무엇 | 작으면 / 크면 | 왜 필요 |
|---|---|---|---|---|
| 1 | `ata_deg` | 내 기수→적 각 | 작다=내가 겨눔(공격) / 크다=적이 옆·뒤 | 공격 기회 여부 |
| 2 | `aa_deg` | 적 꼬리 기준 내 각 | 작다=적 6시(유리) / 크다=정면(위험) | 위치 우열 |
| 3 | `hca` | 진행방향 사잇각 | 작다=평행 추격 / 크다=정반대(정면 교차) | 교전 기하 종류 |
| 4 | `distance_ft` | 거리 | 작다=근접(WEZ권) / 크다=원거리 | 사거리 진입 여부 |
| 5 | `closure_kts` | 접근속도 | +다가옴 / −멀어짐(도망) | 닫히나 벌어지나 |
| 6 | `es_diff` | 에너지 우열 | +내가 우세 / −열세 | 에너지 싸움 |
| 7 | `ego_r_dps` | 내 yaw rate | 내 선회 방향·세기 | 내 기동 상태 |
| 8 | `enm_r_dps` | 적 yaw rate | 적 선회 방향·세기 | 적 기동 예측 |

> 이 8개의 *순서*가 곧 모델 입력 벡터의 순서다(6.6의 `x` 와 일치). 특징을 바꾸면 모델을 다시 구워야 한다(4장).

## 6장. 동작(I): select() 우선순위 사다리 완전 해부

이제 *매 tick 실제로 무슨 일이 일어나는가*. `select()` 를 위에서 아래로 한 줄씩 따라간다.

### 6.0 "우선순위 사다리"라는 발상
`select()` 는 위에서부터 조건을 검사하다 맨 먼저 참이 되는 가지에서 전술을 정하고 즉시 반환한다
(아래로 안 내려감). 위일수록 *더 확실하고 더 중요한* 상황이다.
```
[1] 안전(고도)  ▶  [2] 정면 래치  ▶  [3] 도망  ▶  [4] 근접  ▶  [5] 학습모델
 (위가 이긴다 — 먼저 걸리면 끝)
```

### 6.1 진입과 관측
```python
def select(self, p1, p2) -> Tactic:
    o = compute_obs(p1, p2)        # p1=우리, p2=적 → 관측 o (5장 특징 포함)
```

### 6.2 [1단계] 안전 — 고도 최우선
```python
    if o.ego_alt_ft < self.safe_deck_ft:    # safe_deck_ft = 2500 ft
        return Tactic.CLIMB
```
- 내 고도가 2500ft 미만이면 *다른 모든 판단 무시*하고 `CLIMB`(상승). Hard Deck(1000ft)에서
  1500ft 여유를 두고 미리 끌어올린다.
- *왜 맨 위?* 추락=즉시 패배. 어떤 공격 기회도 생존보다 우선할 수 없다.
- 예: 저공 격렬 기동 중 고도 2300ft → 이번 tick은 무조건 CLIMB. (고도 회복되면 다음부터 다른 전술 복귀.)

### 6.3 [2단계] 정면충돌(head-on) 래치 → ADAPTIVE
```python
    self._tick += 1
    if (self._tick < 50 and o.ata_deg < 40.0 and o.aa_deg > 130.0
            and o.distance_ft < 9000.0):
        self._engaged = True       # 래치(latch)를 켠다
    if self._engaged:
        return Tactic.ADAPTIVE     # 한 번 켜지면 그 경기 내내 ADAPTIVE
```
- 감지 조건(4개 동시): 경기 *초반*(`_tick<50` ≈ 첫 5초) + `ata<40°`(내가 적 향함) +
  `aa>130°`(적도 나를 향함=정면) + `거리<9000ft`. → "이건 정면충돌 매치"라고 판단.
- 래치(latch) = 전등 스위치. 한 번 켜지면(`_engaged=True`) 그 뒤 모든 tick에서 `ADAPTIVE` 만
  반환 → *그 경기 내내 고정*(7.3에서 자세히).
- *왜 고정?* 정면 매치는 `ADAPTIVE`(τ-블렌딩, 여러 기동을 연속 혼합)로 *일관되게* 풀어야 이긴다.
  계측: 끝까지 commit=4/4 승, 도중 전환=1/4. 흔들리면 진다.
- *왜 첫 5초만 감지?* spawn(시작 배치)이 정면인 매치만 잡으려고. 중반에 우연히 잠깐 정면이 돼도
  래치하지 않아야 *중립 추격*이 망가지지 않는다(무회귀).

### 6.4 [3단계] 도망(evasive-extend) → VERTICAL_PURSUIT
```python
    if o.distance_ft > 4500.0 and o.ata_deg < 50.0 and o.closure_kts < 30.0:
        return Tactic.VERTICAL_PURSUIT
```
- 조건: `거리>4500ft`(멀다) + `ata<50°`(내가 적 겨눔) + `closure<30kts`(거의 안 닫힘=적이 도망/extend).
- → `VERTICAL_PURSUIT`(적의 *고도*를 따라가는 수직 추격).
- *왜?* 적이 멀리서 위로 빠질(zoom) 때 수평 추격은 놓친다(계측). 수직 성분을 따라가야 따라붙음.
- *왜 안전한가?* `closure<30` 가드 때문에 *다가오는 적*(closure 큼)에는 발동 안 함 → 공격 상황 무회귀.

### 6.5 [4단계] 근접 마무리 → GUN_TRACK
```python
    if o.distance_ft < 2800.0 and o.ata_deg < 45.0:
        return Tactic.GUN_TRACK
```
- 조건: `거리<2800ft`(WEZ 사거리 근처) + `ata<45°`(대충 정렬).
- → `GUN_TRACK`(적의 선회를 *예측*해 연속 정밀 lead, `ata<12°` 락 시도).
- *왜?* 근접에선 사거리엔 들어가도 overshoot(앞질러 감)로 각이 안 맞아 WEZ=0이 되곤 한다
  (각·거리 *동시* 실패). GUN_TRACK 이 그 둘을 동시에 맞춰 데미지를 만든다.

### 6.6 [5단계] 그 외 — 학습된 회귀모델
```python
    x = [[o.ata_deg, o.aa_deg, _hca(o), o.distance_ft, o.closure_kts,
          _es_diff(o), o.ego_r_dps, o.enm_r_dps]]    # 5장 특징 8개 (이 순서!)
    scores = self.reg.predict(x)[0]                  # 전술별 "점수" 벡터
    return Tactic[self.tactics[int(scores.argmax())]]# 최고점 전술 선택
```
- 1~4단계에 *아무것도 안 걸린* 일반 상황: 특징 8개를 `policy_value.pkl`의 모델에 넣어
  전술별 점수를 받고, 가장 높은 점수의 전술을 고른다.
- 여기가 4장에서 구운 학습 조각이 실제로 쓰이는 유일한 지점. (1~4는 규칙 조각.)

### 6.7 한 장 요약
```
select(o):
  o ← 관측
  if 고도<2500            : return CLIMB              # [1] 안전
  if (초반 & 정면)         : _engaged=켬
  if _engaged             : return ADAPTIVE           # [2] 정면 래치(고정)
  if (멀&겨눔&안닫힘)      : return VERTICAL_PURSUIT   # [3] 도망
  if (가깝&정렬)           : return GUN_TRACK          # [4] 근접
  return 학습모델(특징8개).argmax                       # [5] 일반
```

## 7장. 동작(II): 전술 전환 동역학 — 재평가·dwell·래치

> "한 번 전술이 정해지면, 진행 중에 바뀔 수 있나?" → 그렇다. 단 세 가지 메커니즘이 지배한다.

### 7.1 매 tick 재평가 (기본: 바뀐다)
`select()` 는 0.1초(10Hz)마다 다시 호출되고, 매번 6장의 사다리를 *처음부터* 재검사한다.
상황이 변하면 사다리에서 걸리는 가지가 달라져 전술이 바뀐다.
- 예: 적이 멀 때 → `[3] VERTICAL_PURSUIT` → 따라붙어 가까워지면 → `[4] GUN_TRACK` 으로 *자동 전환*.

### 7.2 dwell — 너무 빠른 전환 막기 (anti-chatter)
매 tick 바뀌면 전술이 깜빡여(chatter) 비행이 불안정해진다. 그래서 매치 루프(`engine/match.py`)에
dwell(머무름) 게이트가 있다. 핵심 규칙:
```python
# _dwell_tactic(제안전술, 현재전술, 현재유지시간 age):
#   제안 ≠ 현재  AND  age ≥ dwell_s(0.3초)  →  전환 (age=0 으로 리셋)
#   그 외                                    →  현재 전술 유지 (age += dt)
```
- 즉 `select()` 가 새 전술을 제안해도, 현재 전술을 0.3초 이상 유지한 뒤에만 실제로 바뀐다.
- 효과: 전술은 *최소 0.3초*는 지속 → 부드러운 전환, 깜빡임 제거.
- 주의: dwell 은 *우리 정책 안*이 아니라 *매치 루프*에 있다(우리·적 공통 적용).

### 7.3 래치 — 유일한 "고정"
[2단계] 정면 래치(`_engaged`)만 예외다. 한 번 켜지면 `select()` 가 *항상* `ADAPTIVE` 를 반환하므로
그 경기 동안 절대 안 바뀐다(의도된 lock). dwell 도 무의미(제안이 늘 같으니).

### 7.4 전환 상태기계 (그림)
```
                 ┌──────────────────────────────────────────────┐
   시작 ─►  [ 동적 모드 ]  매 tick 재평가 → dwell(0.3s) 거쳐 전환     │
              │  CLIMB ↔ VERTICAL_PURSUIT ↔ GUN_TRACK ↔ 학습전술    │
              │                                                    │
              │  (초반 5s 정면 감지)                                 │
              ▼                                                    │
         [ ADAPTIVE 고정 ]  ── 래치 ON → 경기 끝까지 ADAPTIVE ───────┘ (탈출 없음)
```

### 7.5 정리표
| 상황 | 진행 중 전환? | 지배 메커니즘 |
|---|---|---|
| 일반(1·3·4·5단계) | 바뀜 | 매 tick 재평가 + dwell 0.3초 |
| 정면 래치([2]) 발동 후 | 고정(ADAPTIVE) | 래치 |
| 안전([1]) | 고도 회복 시 복귀 | 재평가 |

## 8장. 전술 카탈로그 — 우리 BT가 쓰는 전술들

규칙 조각이 직접 부르는 4개 + 학습 조각이 고를 수 있는 대표 전술.

| Tactic | 한 줄 의미 | 언제 (우리 BT에서) |
|---|---|---|
| `CLIMB` | 상승 (고도 회복) | [1] 고도<2500 |
| `ADAPTIVE` | τ-블렌딩 — 여러 기동을 연속 혼합 | [2] 정면 래치 |
| `VERTICAL_PURSUIT` | 적 고도 따라가는 수직 추격 | [3] 멀고 도망 |
| `GUN_TRACK` | 적 선회 예측 정밀 조준(PN 계열) | [4] 근접 정렬 |
| `LEAD_PURSUIT` | 적 미래 위치를 앞당겨 겨눔 | [5] 학습 선택 가능 |
| `LAG_PURSUIT` | 적 뒤쪽을 겨눠 overshoot 회피 | [5] |
| `ONE_CIRCLE` / `TWO_CIRCLE` | 1원/2원 선회전 기하 | [5] |
| `HIGH_YOYO` / `LOW_YOYO` | 수직 에너지 관리(고/저) | [5] |

> 전술의 *정확한 정의·파라미터*는 [TACTIC_SPEC](../../new_match_engine/TACTIC_SPEC.md), 전술이 만드는
> 실제 setpoint 공식은 `control/guidance.py`.

## 9장. 전술이 실제 비행이 되기까지

`select()` 가 돌려준 `Tactic` 1개는 아래 4단을 거쳐 조종면 움직임이 된다.

```
Tactic
  └─► guidance.py            : 전술 + 관측 → 목표값 Setpoint(방위 ψ*, 고도 h*, 속도 V*)
        └─► autopilot + LQR/INDI : 목표값 → 조종면 u = [throttle, elevator, aileron, rudder]
              └─► plant.py (JSBSim) : u 로 F-16 6자유도 한 스텝 비행
                    └─► judge / WEZ : ATA<12°·500~3000ft → 데미지 / 고도<1000ft → 패배
```
- guidance = "전술"이라는 추상 목표를 *구체 숫자 목표*(어디로 향하고 고도·속도 얼마)로 번역.
- LQR/INDI = 그 목표를 만들기 위해 *조종면을 얼마나 꺾을지* 수학으로 계산(투명·증명 가능).
  (자세히: [LQR 리포트](06_lqr.md), [INDI 검증](08_indi.md).)
- 한 경기 = 이 전체를 제어 20Hz로 반복, 그중 BT(전술 선택)는 10Hz.

## 10장. 워크드 예제 — 한 경기를 틱별로 따라가기

가상의 한 경기를 *대표 순간*만 뽑아, 매 순간 어떤 단계가 걸려 어떤 전술이 왜 선택/전환되는지 본다.
(숫자는 설명용 예시.)

| 시각 | 관측(요약) | 걸린 단계 | 전술 | 왜 |
|---|---|---|---|---|
| 0.0s | dist 3300, ata 91, aa 89 (beam) | [5] 학습 | (모델 선택) | 정면 아님(aa 89<130)·근접 아님 → 학습이 결정 |
| 0.3s | ata 35, aa 150, dist 8000 (정면 전개) | [2] 감지 | ADAPTIVE | 초반·정면 4조건 충족 → `_engaged` 켜짐 |
| 0.3s~끝 | (무엇이 와도) | [2] 래치 | ADAPTIVE | 래치 ON → 경기 내내 고정 (7.3) |

다른 경기(정면 래치 *안* 걸린 경우):
| 시각 | 관측 | 단계 | 전술 | 비고 |
|---|---|---|---|---|
| 2.0s | dist 6000, ata 30, closure −10 (적 도망) | [3] | VERTICAL_PURSUIT | 멀고 안 닫힘 |
| 6.0s | dist 5200, ata 25, closure +5 | [3] | VERTICAL_PURSUIT | 여전히 멀고 추격 중 |
| 6.3s | dist 4400, ata 28, closure +40 | [5] | (학습) | closure>30 → [3] 탈락, dwell 거쳐 전환 |
| 9.0s | dist 2600, ata 40 | [4] | GUN_TRACK | 근접 사거리 진입 → 마무리 |
| 9.2s | (저공으로 끌려감) 고도 2400 | [1] | CLIMB | 안전 최우선, GUN_TRACK 무시 |
| 9.6s | 고도 2700 회복, dist 2500, ata 38 | [4] | GUN_TRACK | 고도 회복 → 다시 마무리 |

→ 이 예제가 7장(재평가·dwell·래치)을 그대로 보여준다: 대부분 동적 전환, 안전은 끼어들기, 정면만 고정.

## 부록 A. 용어집
| 용어 | 정의 |
|---|---|
| tick | 결정의 최소 시간 단위. BT는 10Hz(0.1s). |
| Observation | 적과의 기하·상태 숫자 묶음(거리·ATA·AA·HCA·closure·es_diff·yaw rate). |
| ATA / AA / HCA | 내기수→적각 / 적꼬리기준 내각 / 진행방향 사잇각. |
| closure | 거리 변화율(+접근/−이격). |
| es_diff | 에너지(고도+속도) 우열, ft 등가. |
| Tactic | 기동의 추상 이름(GUN_TRACK 등 16종). |
| Policy(정책) | 관측→행동 함수 `π`. 우리 BT = TreePolicy. |
| dispatch | 상황별로 옳은 전술을 강제하는 규칙 분기. |
| 래치(latch) | 한 번 켜지면 유지되는 상태(정면→ADAPTIVE 고정). |
| dwell | 전환을 최소 0.3초 지연하는 anti-chatter 게이트. |
| WEZ | ATA<12°·500~3000ft → 데미지 구역. |
| Hard Deck | 1000ft 미만=패배. |

## 부록 B. 점검 문제 (이해 확인)
1. 우리 BT는 1초에 몇 번 호출되나? (답: 10번, 10Hz)
2. 고도 2400ft에서 적을 완벽히 겨눴다(ata 5°, 근접). 어떤 전술? (답: CLIMB — [1] 안전이 [4]보다 위)
3. 정면 래치가 켜진 뒤 적이 도망가면 전술은? (답: ADAPTIVE 고정 — 래치)
4. select가 매 tick GUN_TRACK→LEAD_PURSUIT를 번갈아 제안하면 실제로 깜빡이나? (답: 아니오 — dwell 0.3초가 막음)
5. 학습 조각(회귀)이 보는 특징은 몇 개이고 어디서 굽나? (답: 8개, offline_solver→policy_value.pkl)
